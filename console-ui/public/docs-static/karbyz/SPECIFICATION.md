# Спецификация языка Карбыз

| Поле | Значение |
|------|----------|
| Идентификатор языка | Karbyz / Карбыз |
| Версия языка | 1.0 |
| Версия документа | 1.3.0 |
| Статус | нормативный |
| Метаязык синтаксиса | РБНФ |
| Целевая платформа | Watermelon CI |
| Расширение исходных файлов | `.kbz` |
| Кодировка исходного текста | UTF-8 |

Настоящий документ определяет лексику, синтаксис, статическую и динамическую семантику языка Карбыз.
Карбыз — поверхностный синтаксис манифеста пайплайна Watermelon CI (наравне с YAML-формой) и императивных
конструкций сценария. Документ не является руководством пользователя.

---

## 1. Область применения и соответствие

### 1.1. Область применения

Карбыз описывает пайплайн Watermelon CI тем же смыслом, что YAML-манифест: стадии, команды, узлы —
плюс императивные средства сценария. Реализация обязана:

1. анализировать исходный текст на соответствие настоящей спецификации;
2. отображать платформенные конструкции (§10) на единую модель пайплайна платформы;
3. компилировать корректный манифест в Jenkinsfile тем же конвейером, что YAML;
4. при необходимости исполнять программу (динамическая семантика).

### 1.2. Нормативные соглашения записи

В РБНФ:

- `"терминал"` — терминальный символ;
- `Нетерминал` — нетерминальный символ;
- `A \| B` — альтернатива;
- `[ X ]` — необязательность;
- `{ X }` — повторение ноль или более раз;
- правило завершается `.`

В семантических правилах модальности:

- **должен** — обязательное требование;
- **не должен** — запрет;
- **может** — допустимое поведение реализации.

### 1.3. Соответствие реализации

Реализация соответствует версии 1.0, если:

- отвергает программы, нарушающие лексику или синтаксис (§2–§3, §11);
- для синтаксически корректных программ выполняет семантические проверки (§4–§9);
- для семантически корректных программ обеспечивает наблюдаемое поведение, описанное в §§5–10;
- формирует диагностику по §12;
- при компиляции манифеста соблюдает модель §10 (эквивалентность YAML-форме).

## 2. Лексическая структура

### 2.1. Исходный текст

Исходный текст — последовательность скалярных значений Unicode в кодировке UTF-8.  
Транслятор должен читать текст слева направо и формировать поток лексем.

### 2.2. Пробельные символы

Символы `U+0020`, `U+0009`, `U+000D`, `U+000A` разделяют лексемы и не входят в значимый поток, за исключением их роли внутри строковых литералов.

### 2.3. Комментарии

Лексема комментария начинается с `#` вне строкового литерала и продолжается до конца строки (не включая символ перевода строки). Комментарии удаляются на этапе лексического анализа.

### 2.4. Классы лексем

| Класс | Обозначение | Определение |
|-------|-------------|-------------|
| ключевое слово | `keyword` | §2.6 |
| идентификатор | `ident` | §2.5 |
| целочисленный литерал | `number` | одна или более десятичных цифр |
| строковый литерал | `string` | §2.7 |
| присваивание | `assign` | последовательность `<-` |
| открытие блока | `open` | последовательность `::` |
| оператор | `op` | §2.8 |
| разделитель | `punct` | один из `( ) [ ] , .` |
| конец ввода | `eof` | искусственная лексема |

Двухсимвольные лексемы `<-`, `::`, `==`, `!=`, `<=`, `>=`, `&&`, `||` распознаются предпочтительно перед односимвольными.

### 2.5. Идентификаторы

```
Ident = Letter { Letter | Digit | "_" } .
Letter = /* Unicode Letter */ | "_" .
Digit  = "0"…"9" .
```

Регистр идентификаторов значим. Идентификатор не должен совпадать с ключевым словом после нормализации ключевых слов (§2.6).

### 2.6. Ключевые слова

Регистр ключевых слов не значим: входная лексема приводится к нижнему регистру до классификации.
Алфавит — обычная кириллица/латиница без ә, ө, ү, җ, ң, һ.

| Обозначение | Перевод | Роль |
|-------------|---------|------|
| `сан` | число | тип: целое |
| `суз` | слово / строка | тип: Unicode-строка |
| `тезма` | ряд / массив | тип: список |
| `дорес` | истина | логическая константа |
| `ялган` | ложь | логическая константа |
| `жыелма` | собрание / модуль | единица компиляции |
| `ахыр` | конец | закрытие блока/модуля |
| `::` | открыть блок | начало составного оператора (§2.4 `open`) |
| `<-` | присвоить | связывание (§2.4 `assign`) |
| `агар` | если | условие |
| `булса` | то | then |
| `юкса` | иначе | else |
| `шулай` | пока так | while |
| `вакыт` | время / пока | хвост while |
| `очен` | для | for |
| `да` | и / до | зона for |
| `кадак` | шаг | зона for |
| `эшлама` | работа / функция | объявление функции |
| `кайтар` | вернуть | return |
| `керт` | ввести | stdin |
| `чыгар` | вывести | stdout |
| `озынлык` | длина | длина суз/тезма |
| `хам` | и | логическое И |
| `яки` | или | логическое ИЛИ |
| `тугел` | не | логическое НЕ |
| `этап` | этап | стадия CI |
| `башкар` | исполнить | команда оболочки |
| `сервер` | сервер / узел | целевой хост |

#### Группы (для ссылок)

- типы/константы: `сан`, `суз`, `тезма`, `дорес`, `ялган`
- структура: `жыелма`, `ахыр`
- управление: `агар`, `булса`, `юкса`, `шулай`, `вакыт`, `очен`, `да`, `кадак`, `кайтар`
- объявления: `эшлама`
- I/O: `керт`, `чыгар`, `озынлык`
- логика: `хам`, `яки`, `тугел`
- платформа: `этап`, `башкар`, `сервер`

### 2.7. Строковые литералы

Строковый литерал начинается и заканчивается `"`. Внутри допускаются экранирования:

| Последовательность | Значение |
|--------------------|----------|
| `\\` | `\` |
| `\"` | `"` |
| `\n` | перевод строки |
| `\t` | табуляция |

Незакрытый литерал — ошибка лексического анализа.

### 2.8. Операторы выражения

`+`, `-`, `*`, `/`, `%`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `&&`, `||`, `!`

## 3. Синтаксис программы

Полная грамматика приведена в §11. В этом разделе фиксируется структура верхнего уровня.

### 3.1. Единица компиляции

Единица компиляции — один модуль:

```
жыелма ModuleName ::
  { DeclarationOrStatement }
ахыр жыелма .
```

`ModuleName` — `ident`. Имя в заголовке и в завершителе должно совпадать лексически; в версии 1.0 реализация должна требовать наличие обоих вхождений `жыелма` по грамматике; проверка равенства имён — рекомендуемое расширение, не обязательное для 1.0.

### 3.2. Порядок элементов модуля

Элементы модуля обрабатываются в порядке записи. Объявления функций могут встречаться до использования; реализация должна регистрировать все `эшлама` модуля до исполнения прочих операторов верхнего уровня.

## 4. Система типов

### 4.1. Типы значений

| Тип | Ключевое слово | Носитель | Примечание |
|-----|----------------|----------|------------|
| целочисленный | `сан` | целое со знаком произвольной точности реализации не менее 32 бит | литералы без суффиксов |
| строковый | `суз` | последовательность скаляров Unicode | |
| массив | `тезма` | упорядоченная последовательность значений | индексы с нуля |
| логический | — | `дорес`, `ялган` | не объявляется как тип переменной |

### 4.2. Совместимость

При объявлении и присваивании тип правой части должен совпадать с типом левой:

- `сан` ← целочисленное значение;
- `суз` ← строковое значение;
- `тезма` ← значение-массив.

Неявные преобразования запрещены, за исключением правила конкатенации (§5.4).

| Ситуация | Фаза | Результат |
|----------|------|-----------|
| `сан x <- "a"` | семантика / исполнение | ошибка; связывание не выполняется |
| `суз s <- 1` | семантика / исполнение | ошибка |
| `тезма a <- 0` | семантика / исполнение | ошибка |
| присваивание необъявленному имени | семантика / исполнение | ошибка |
| повторное объявление имени в той же `Env` | семантика / исполнение | ошибка |

### 4.3. Логический контекст

В условиях операторов `агар`, `шулай`, `очен` значение приводится к логическому по правилам:

| Значение | Истина? |
|----------|---------|
| `дорес` | да |
| `ялган` | нет |
| `сан` = 0 | нет |
| `сан` ≠ 0 | да |
| `суз` длины 0 | нет |
| иная `суз` | да |
| `тезма` длины 0 | нет |
| иная `тезма` | да |

### 4.4. Объекты среды исполнения

Реализация оперирует следующими объектами времени исполнения:

| Объект | Описание |
|--------|----------|
| `Module` | модуль: имя, список определений функций, тело |
| `Function` | имя, список параметров `(Type × Name)`, тело |
| `Env` | таблица связываний имён с парами `(Type, Value)` и ссылкой на родительскую область |
| `Value` | значение одного из носителей §4.1 |
| `Stage` | именованный этап платформы |
| `Host` | именованный целевой узел |
| `Command` | строка команды оболочки, порождённая `башкар` |
| `Diagnostic` | фаза, позиция, код/текст |

## 5. Выражения

### 5.1. Приоритет и ассоциативность

От низшего приоритета к высшему:

| Уровень | Операторы | Ассоциативность |
|---------|-----------|-----------------|
| 1 | `яки`, `||` | левая |
| 2 | `хам`, `&&` | левая |
| 3 | `тугел`, `!` | правая (префикс) |
| 4 | `== != < <= > >=` | левая |
| 5 | `+ -` | левая |
| 6 | `* / %` | левая |
| 7 | унарные `+ -` | правая |
| 8 | вызов, индекс, первичные | — |

### 5.2. Арифметика на `сан`

Операции `+ - * / %` над двумя `сан` дают `сан`.  
`/` — целочисленное деление с отсечением дробной части по направлению к нулю.  
`%` — остаток, согласованный с `/`.  
Деление на ноль — ошибка исполнения.

### 5.3. Сравнения

Операции `== != < <= > >=` определены для пары значений совместимых носителей (`сан`–`сан`, `суз`–`суз`). Результат — логический. Сравнение массивов целиком в версии 1.0 не определяется (ошибка семантики/исполнения).

### 5.4. Конкатенация

Если хотя бы один операнд `+` имеет тип `суз`, операция означает конкатенацию строк: второй операнд преобразуется к текстовому представлению (`сан` — десятичная запись; логический — `истина`/`ложь` в сообщениях среды; массив — каноническая печатная форма реализации).

### 5.5. Логические связки

| Операция | Операнды | Результат | Семантика |
|----------|----------|-----------|-----------|
| `e1 хам e2`, `e1 && e2` | любые (через §4.3) | логический | короткое замыкание: если `e1` ложен в §4.3 — `ялган`, `e2` не вычисляется; иначе результат = логический контекст `e2` |
| `e1 яки e2`, `e1 \|\| e2` | любые (через §4.3) | логический | короткое замыкание: если `e1` истинен в §4.3 — `дорес`, `e2` не вычисляется; иначе результат = логический контекст `e2` |
| `тугел e`, `! e` | любой (через §4.3) | логический | `дорес`, если операнд ложен; иначе `ялган` |

Логический результат в выражениях представлен значениями `дорес` / `ялган`. Отдельного типа переменной для логики нет (§4.1).

### 5.6. Индексация

`a[i]` требует: `a` — `тезма`, `i` — `сан`, `0 ≤ i < озынлык(a)`. Иначе — ошибка исполнения.  
Тип результата — тип элемента (динамический носитель значения элемента).

### 5.7. Вызов функции

`f(e1,…,en)` — см. §7. Тип результата — тип выражения `кайтар` (или пустой результат, если `кайтар` без значения / отсутствует).

### 5.8. Встроенная операция длины

`озынлык(e)` определена для `суз` и `тезма`, результат — `сан`. Для прочих типов — ошибка.

### 5.9. Литерал массива

`[ e1, …, en ]` создаёт `тезма` из значений выражений в порядке записи.

### 5.10. Условные выражения (`Cond`)

Нетерминал `Cond` в операторах `агар`, `шулай`, `очен` — это обычное `Expr` (§11). Отдельного синтаксиса «логического выражения» нет.

#### 5.10.1. Где используется

| Конструкция | Место Cond | Правило |
|-------------|------------|---------|
| `агар ( Cond ) булса …` | условие ветвления | вычислить `Cond`; если истинен по §4.3 — `ThenPart`, иначе `ElsePart` (если есть) |
| `шулай ( Cond ) вакыт …` | условие продолжения цикла | перед каждой итерацией; ложь → выход |
| `очен ( Init да Cond кадак Step )` | условие продолжения | после `Init`, затем перед каждой итерацией; ложь → выход |

#### 5.10.2. Что допустимо в `Cond`

Любое `Expr`, результат которого можно привести к логическому контексту (§4.3):

| Вид Cond | Пример | Истинность |
|----------|--------|------------|
| сравнение | `n < 10`, `s == "ok"` | результат сравнения (`дорес`/`ялган`) |
| логическая связка | `n > 0 хам n < 100`, `a яки b` | §5.5 |
| отрицание | `тугел готово`, `! флаг` | §5.5 |
| переменная / вызов | `флаг`, `пусто(xs)` | §4.3 к значению |
| литерал | `дорес`, `ялган`, `0`, `""` | §4.3 |
| арифметика | `n % 2` | `сан ≠ 0` → истина |

Тип Cond **не обязан** быть логическим литералом: `агар (счётчик) булса` допустим — `счётчик` как `сан` проверяется по §4.3.

#### 5.10.3. Примеры

```
агар (n > 0 хам n < 10) булса ::
  чыгар ("в диапазоне")
юкса ::
  чыгар ("вне")
ахыр

шулай (i < озынлык (xs)) вакыт ::
  чыгар (xs[i])
  i <- i + 1
ахыр

очен (сан j <- 0 да j < 3 кадак j <- j + 1) ::
  чыгар (j)
ахыр
```

#### 5.10.4. Ошибки в Cond

| Ситуация | Фаза | Результат |
|----------|------|-----------|
| ошибка во вложенном Expr (деление на 0, плохой индекс, …) | исполнение | Cond не вычисляется до конца; тело не выполняется |
| сравнение `тезма` с `тезма` | семантика / исполнение | ошибка (§5.3) |
| сравнение разнотипных носителей (`сан` с `суз`) | семантика / исполнение | ошибка |

### 5.11. Сводная таблица: операция → типы → результат

Обозначения: `L` / `R` — типы операндов; `лог` — значение `дорес`\|`ялган`; `∅` — ошибка.

| Операция | L | R | Результат | Примечание |
|----------|---|---|-----------|------------|
| `+ - * / %` | `сан` | `сан` | `сан` | `/` `%` — к нулю; `/0` — ошибка |
| унарные `+ -` | `сан` | — | `сан` | |
| `+` (конкат.) | `суз` | любой | `суз` | R → текст (§5.4) |
| `+` (конкат.) | любой | `суз` | `суз` | L → текст |
| `== !=` | `сан` | `сан` | `лог` | |
| `== !=` | `суз` | `суз` | `лог` | |
| `< <= > >=` | `сан` | `сан` | `лог` | |
| `< <= > >=` | `суз` | `суз` | `лог` | лексикографически |
| сравнения | `тезма` | * | `∅` | не определены в 1.0 |
| сравнения | разные носители | * | `∅` | |
| `хам` `&&` `яки` `\|\|` | * | * | `лог` | через §4.3; short-circuit |
| `тугел` `!` | * | — | `лог` | через §4.3 |
| `a[i]` | `тезма` | `сан` | элемент | границы обязательны |
| `озынлык(e)` | `суз`\|`тезма` | — | `сан` | иначе `∅` |
| литерал числа | — | — | `сан` | |
| литерал строки | — | — | `суз` | |
| `дорес` `ялган` | — | — | `лог` | |
| `[…]` | — | — | `тезма` | |

Правило выбора для `+`: если хотя бы один операнд `суз` — конкатенация (§5.4); иначе оба должны быть `сан` — арифметика (§5.2). Иначе — ошибка.

## 6. Операторы

### 6.1. Блок

`:: { Statement } ахыр` создаёт вложенную область `Env`.

### 6.2. Объявление переменной

`Type Ident [ <- Expr ]`

При отсутствии инициализатора используются значения по умолчанию: `сан` → `0`, `суз` → `""`, `тезма` → `[]`.  
Повторное объявление имени в текущей `Env` запрещено.

### 6.3. Присваивание

`Ident <- Expr`  
`Ident [ Expr ] <- Expr`

Левая часть должна быть ранее объявлена. Для индексного присваивания целевой объект должен иметь тип `тезма`.

### 6.4. Условный оператор

```
агар ( Cond ) булса ::
  ThenPart
[ юкса ::
  ElsePart ]
ахыр
```

`Cond` — выражение по §5.10. Исполняется `ThenPart`, если Cond истинен в смысле §4.3; иначе при наличии — `ElsePart`.  
`ThenPart` / `ElsePart` — последовательности `Statement` в области блока.

### 6.5. Цикл `шулай`

```
шулай ( Cond ) вакыт :: Body ахыр
```

`Cond` — §5.10. Пока Cond истинен, исполняется `Body` в новой области на каждую итерацию (локальные объявления тела не переживают итерацию).

### 6.6. Цикл `очен`

```
очен ( Init да Cond кадак Step ) :: Body ахыр
```

1. Выполнить `Init` в области цикла (если задан).  
2. Пока `Cond` (§5.10) истинен: выполнить `Body`, затем `Step` (если задан).

`Init` — объявление (`Type Ident <- Expr`) или присваивание (`Ident <- Expr`).  
`Step` — присваивание (`Ident <- Expr`).  
`Cond` вычисляется заново перед каждой итерацией; побочные эффекты в Cond допускаются, но не рекомендуются.

### 6.7. Возврат

`кайтар [ Expr ]` завершает исполнение текущей функции и передаёт значение (или пустой результат). Вне функции — ошибка.

### 6.8. Вызов как оператор

`Ident ( Args )` вычисляет вызов и отбрасывает результат.

### 6.9. Вывод

`чыгар ( [ Expr { , Expr } ] )` печатает текстовые представления аргументов, разделённые одним пробелом, затем перевод строки в стандартный поток вывода.

### 6.10. Ввод

`керт ( Type Ident )` читает одну строку из стандартного ввода (без завершающего перевода строки), объявляет `Ident` типа `Type` и связывает значение.

| Type | Правило разбора | При нарушении |
|------|-----------------|---------------|
| `сан` | вся строка должна быть десятичным целым со знаком (опциональный ведущий `-`, затем одна или более цифр); пробелы по краям не допускаются | ошибка исполнения; связывание не создаётся |
| `суз` | строка как есть (включая пустую) | — |
| `тезма` | не поддерживается в 1.0 | ошибка семантики |

Пример отказа:

```
керт (сан n)
```

при вводе `abc` или `12.5` или ` 3 ` — ошибка исполнения фазы `исполнение`, процесс транслятора завершается с ненулевым кодом.

Конец потока ввода до получения строки — ошибка исполнения «конец ввода».

### 6.11. Платформенные операторы

См. §10.

## 7. Функции

### 7.1. Объявление

```
эшлама Name ( [ Type Ident { , Type Ident } ] ) ::
  Body
ахыр
```

Имя функции уникально в модуле. Параметры образуют начальные связывания локальной `Env`, родитель — глобальная среда модуля.

### 7.2. Вызов

Число аргументов должно равняться числу параметров. Каждый аргумент должен быть совместим с типом параметра (§4.2).  
При отсутствии `кайтар` результат вызова пуст.

---

## 8. Области видимости и связывания

Поиск имени выполняется в текущей `Env`, затем в родителях до глобальной.  
Присваивание изменяет ближайшее существующее связывание; необъявленное имя — ошибка.  
Параметры функции и локальные объявления скрывают одноимённые внешние связывания.

---

## 9. Модуль и точка входа

Исполнение модуля:

1. построить таблицу функций;
2. последовательно исполнить операторы верхнего уровня, не являющиеся объявлениями функций.

Отдельной функции `main` нет.

## 10. Манифест Watermelon CI (модель пайплайна)

Карбыз и YAML — два синтаксиса одной модели манифеста. Платформенные операторы ниже и есть запись этой модели; YAML не является «выходным форматом» Карбыза.

### 10.1. Оператор этапа

```
этап StringLit :: Body ахыр
```

Смысл: стадия пайплайна с именем `StringLit`.  
При исполнении: метка этапа и исполнение `Body`.  
В модели: job с `stage` = литерал; тело — список `script`.

### 10.2. Оператор команды

```
башкар Expr
```

`Expr` должен давать `суз`. Команда стадии (элемент `script`).  
При исполнении: регистрация / трассировка; оболочка — только в явном режиме.  
Вне этапа попадает в синтетический stage `shell`.

### 10.3. Оператор узла

```
сервер StringLit :: Body ахыр
```

Группа команд узла `StringLit` → stage `host-<имя>` в той же модели.

### 10.4. Каноническая модель

Независимо от синтаксиса (.kbz или YAML) манифест задаёт:

- `name` — имя пайплайна (`жыелма`);
- `stages` — упорядоченный список стадий;
- `jobs.<id>.stage` — имя стадии;
- `jobs.<id>.script` — команды.

Целевой артефакт CI-конвейера — Declarative Jenkinsfile (тот же компилятор, что для YAML).

## 11. Нормативная РБНФ

```
Program = "жыелма" Ident "::" { DeclOrStmt } "ахыр" "жыелма" "." .

DeclOrStmt = VarDecl | FuncDecl | Statement .

VarDecl = Type Ident [ "<-" Expr ] .
Type = "сан" | "суз" | "тезма" .

FuncDecl = "эшлама" Ident "(" [ Param { "," Param } ] ")" Block .
Param = Type Ident .

Statement =
    VarDecl
  | Assign
  | IfStmt
  | WhileStmt
  | ForStmt
  | ReturnStmt
  | CallStmt
  | PrintStmt
  | InputStmt
  | StageStmt
  | RunStmt
  | HostStmt .

Block = "::" { Statement } "ахыр" .
Assign = Ident [ "[" Expr "]" ] "<-" Expr .

IfStmt = "агар" "(" Expr ")" "булса" "::" { Statement }
         [ "юкса" "::" { Statement } ] "ахыр" .
WhileStmt = "шулай" "(" Expr ")" "вакыт" Block .
ForStmt = "очен" "(" ForInit "да" Expr "кадак" ForStep ")" Block .
ForInit = [ Type Ident "<-" Expr | Ident "<-" Expr ] .
ForStep = [ Ident "<-" Expr ] .

ReturnStmt = "кайтар" [ Expr ] .
CallStmt = Ident "(" [ Expr { "," Expr } ] ")" .
PrintStmt = "чыгар" "(" [ Expr { "," Expr } ] ")" .
InputStmt = "керт" "(" Type Ident ")" .
StageStmt = "этап" StringLit Block .
RunStmt = "башкар" Expr .
HostStmt = "сервер" StringLit Block .

Expr = OrExpr .
OrExpr = AndExpr { ("яки" | "||") AndExpr } .
AndExpr = NotExpr { ("хам" | "&&") NotExpr } .
NotExpr = ("тугел" | "!") NotExpr | RelExpr .
RelExpr = AddExpr { ("=="|"!="|"<"|"<="|">"|">=") AddExpr } .
AddExpr = MulExpr { ("+"|"-") MulExpr } .
MulExpr = Unary { ("*"|"/"|"%") Unary } .
Unary = ("+"|"-") Unary | Primary .
Primary =
    Ident [ "(" [ Expr { "," Expr } ] ")" | "[" Expr "]" ]
  | Number | StringLit | "дорес" | "ялган"
  | "[" [ Expr { "," Expr } ] "]"
  | "(" Expr ")"
  | "озынлык" "(" Expr ")" .
```

## 12. Транслятор: фазы и взаимодействие

### 12.1. Фазы

| № | Фаза | Вход | Выход | Ответственность |
|---|------|------|-------|-----------------|
| 1 | Лексический анализ | исходный текст | поток лексем | классификация, позиции |
| 2 | Синтаксический анализ | лексемы | AST | рекурсивный спуск по §11 |
| 3 | Семантический анализ | AST | аннотированный AST / отказ | типы, области, арность |
| 4a | Исполнение | модель / AST | эффекты I/O, команды | динамическая семантика |
| 4b | Компиляция | модель пайплайна | Jenkinsfile | §10.4 |

Фазы 1–3 обязательны для любого режима. Режим выбирает 4a и/или 4b. YAML-форма — лишь каноническая сериализация той же модели для существующего компилятора, не отдельный продукт языка.

### 12.2. Проходы транслятора

| Участок | Проходность | Пояснение |
|---------|-------------|-----------|
| лексер ↔ парсер | однопроходный | парсер запрашивает следующую лексему по мере разбора; повторного чтения исходного текста нет |
| семантический анализ | после AST | выполняется по построенному дереву единицы компиляции |
| исполнение / Jenkinsfile | после AST | отдельный проход по модели; не совмещён с парсингом |

Итого: анализ исходника — однопроходный (лексер обслуживает парсер). Классического однопроходного компилятора «сразу в целевой код во время разбора» нет: генерация Jenkinsfile и исполнение идут по готовому AST/модели.

### 12.3. Диагностика

Сообщение об ошибке должно содержать:

1. фазу: `лексер` | `синтаксис` | `семантика` | `исполнение`;
2. позицию `строка:столбец` (1-based), если известна;
3. текст нарушения.

При ошибке фаз 1–3 компиляция (§10) не выполняется. Код завершения процесса транслятора при ошибке — ненулевой.
